SaaS Roadmap

Piano Maintainer To-Do

This document outlines the work needed to turn the current Django app into a production-ready multi-company SaaS platform.

The app is already in a solid early product shape: one Django project, one main domain app, template-driven UI, custom technician auth, CSV/reporting, and background-style scheduling via a management command. The next phase is mostly about tenancy, security, account lifecycle, and operational hardening.

Current Structure Snapshot

Project Layout

  • piano_maintainer/: Django settings, URL routing, ASGI/WSGI.
  • maintenance/: main business app containing models, views, forms, admin, tests, services, and management commands.
  • maintenance/templates/: server-rendered UI, including partials and registration pages.
  • maintenance/static/: app CSS and bundled HTMX.

What This Means

  • The app is currently effectively single-tenant in its domain model.
  • Auth exists, but true organization/company isolation is not fully modeled yet.
  • The current codebase is small enough that tenancy can still be added cleanly before the system becomes much harder to untangle.

  2. Audit logging. Done for v1 in embedded form: key create, update, workflow, and admin events are logged centrally in AuditLog, and recent activity is shown inline on piano, organization, venue, and work order detail pages rather than in a separate audit console.
  3. Soft-delete and recovery policy. Decide what can be restored and what must remain immutable after completion.
  4. Email infrastructure. In progress: password reset and invitation flows exist, but production email delivery still needs live operational verification.
  5. Authorization layer cleanup. Done in the primary app flows: membership-based permissions now drive active-company authorization.
  6. Tenant-safe background jobs. Done for scheduled work-order generation, which now runs outside page views and respects tenant-owned records.
  7. Tenant-safe exports. Done for the current CSV/report exports in the main UI.
  8. File and media access control. Done for photos: delivery is authenticated, company-scoped, and uses signed URLs in object storage.
  9. Onboarding flow. Partly done: there is now a first-run setup checklist, a bootstrap command for new environments, and clearer tenant-admin setup visibility.
  10. Search and filter hardening. Every lookup path must be company-scoped, including autocomplete and background actions.
  11. Admin experience for tenant support. Decide whether there is a platform super-admin role outside company admins.
  12. Environment separation. In progress: deployment env vars, bootstrap steps, and tenant-targeted operational commands are documented, with more production hardening still ahead.
  13. Error monitoring and backups. Needed before multiple businesses depend on the app.
  14. Security review. Validate password policy, session handling, CSRF settings, upload rules, and authorization checks.
  15. Historical data strategy. The legacy private-use database can remain separate, but the SaaS branch still needs a clean seed/import story for demo and onboarding data.

SaaS Branch Standards

The SaaS branch should now be treated as a clean multi-tenant product track with its own fresh database. The legacy private-use database does not need to constrain schema or authorization design on this branch.

  1. Make the schema fully SaaS-native. All tenant-owned records should use required company relationships, membership-based permissions should become the primary authorization model, and company settings should remain company-scoped rather than singleton-style.
  2. Remove transitional legacy helpers. Default-company autofill, compatibility fallbacks, and any logic kept only to protect the older single-tenant database should be removed before deployment.
  3. Treat media as private from day one. New uploads should be private by default, company-authorized through Django, and delivered with short-lived signed URLs.
  4. Target a fresh Postgres deployment. This branch should be prepared for a new production database with clean migrations, seed/demo data where helpful, and no requirement to support in-place upgrade from the private legacy database.

Next Steps

  1. Production readiness validation. Verify empty Postgres bootstrap, production email backend behavior, object storage access, and deployment/runbook documentation end to end.
  2. Tenant admin lifecycle polish. Add member reactivation shortcuts, clearer membership-state messaging, and stronger self-serve admin workflows around role changes and account cleanup.
  3. Platform operations policy. Define support/admin behavior outside tenant admins, decide what non-tenant staff can see and do, and document backups, monitoring, and incident ownership.
  4. Final SaaS readiness pass. Re-check exports, reports, background jobs, media security, and production cutover readiness so there are no remaining cross-company leaks or launch blockers.
